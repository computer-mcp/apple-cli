# Notes Capability List

## Scope / Purpose

This target-owned capability list records the accepted and gated `apple notes`
command surface, implementation mechanism, verifier, and safety gate for
Notes.app workflows. Current Notes architecture truth lives in
`Architecture.md`; ordinary usage lives in
`../../Reference/Notes/UserGuide.md`.

The target design goal is semantic CLI coverage for accepted Notes.app account,
folder, note, rich-content, organization, import/export, and diagnostic
workflows. Private Notes frameworks are the intended production implementation
mechanism for accepted reads and writes. Read-only store/index inspection
supports semantic read enrichment, doctor diagnostics, parity checks, and
post-mutation verification.

## Accepted Capability Gate

A Notes capability is accepted only when it has all of the following:

- semantic command shape in Notes user terms
- target-local safety policy, including `DryRun` for mutations and explicit
  allow flags where external dispatch, destructive selection, or collaboration
  impact exists
- typed private framework implementation path
- verifier rule using private framework readback and optional read-only
  store/index evidence
- tests for parsing, JSON shape, dry-run payloads, implementation dispatch,
  supported failure behavior, verifier behavior, and privacy boundaries
- documentation in this capability list and the Notes user/developer guides

Raw SDEF support, private symbol presence, SQLite rows, or a local manual
experiment do not make a capability accepted.

Closeout status uses a narrower daily-use milestone boundary than the full
future backlog. Supported records are implemented Notes CLI behavior with a
private-framework path and verifier. Delegated records are accounted system,
Notes.app UI, or external-app owner boundaries and must not execute Notes CLI
implementation calls. Gated records are future private-framework backlog when a
capability may belong in the CLI but still needs a safe selector route,
secret/artifact boundary, and private readback verifier. Advanced
password-method migration/rekey for existing locked notes, `state
change-password`, and legacy `settings password` are future gated
password/security backlog, not current closeout blockers.

## Implementation Selection Rules

- Use private Notes frameworks for accepted Notes reads and writes.
- Keep the full-dump-derived module import boundary as the compile contract.
- Use read-only Notes SQLite reading to enrich normal reads, support doctor
  output, and verify post-write state.
- Use AppleScript only as a read-only parity reader, not as a production
  fallback or writer.
- Keep command names semantic and user-facing.
- Reject direct Notes SQLite writes.

## Validation And Proof Expectations

- Package tests cover command parsing, JSON output, dry-run payload shape,
  private implementation dispatch, read enrichment, supported error behavior,
  doctor output, verifier behavior, and AppleScript migration removal.
- Private framework mutations use method availability checks, preflight,
  dry-run summaries, execution gates where needed, private framework readback,
  read-only store/index verification, and preservation checks.
- Store diagnostics may expose implementation evidence in doctor output; normal
  commands stay semantic and user-facing.
- Static or test guardrails should prevent direct Notes store write SQL.
